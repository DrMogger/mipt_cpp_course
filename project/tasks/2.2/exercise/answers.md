# Упражнение 2.2: предсказания до запуска

Программа не собиралась и не запускалась. Ниже записаны предсказания
для Linux x86-64 с GCC/Clang: `int` занимает 4 байта и выравнивается на 4,
указатель и `double` — 8 байт с выравниванием на 8.
Размеры и смещения относятся к этому ABI; стандарт C++ не задаёт
универсальные численные значения для всех реализаций.

## 1. Порядок конструкторов и деструкторов

Ожидаемые 13 строк без заголовка раздела:

```text
  + база First
  + база Second
  + поле один
  + поле два
  + поле три
  + тело Derived
  (объект живёт)
  - тело Derived
  - поле три
  - поле два
  - поле один
  - база Second
  - база First
```

Сначала создаются базы в порядке их перечисления в объявлении класса:
`First`, затем `Second`. Потом создаются поля в порядке объявления:
`one_`, `two_`, `three_`. Только после этого выполняется тело конструктора.

Запись `two_("два"), one_("один"), three_("три")` в списке инициализации
не меняет порядок создания полей. Ожидается предупреждение о несовпадении
порядка инициализаторов с порядком объявления `two_` и `one_`
(`-Wreorder` или `-Wreorder-ctor`). Это предсказание диагностики,
а не результат сборки.

При разрушении сначала выполняется тело деструктора `Derived`, затем
разрушаются поля в обратном порядке, затем базы в обратном порядке.

## 2. Размеры и выравнивание

| Тип | Ожидаемый `sizeof` | Ожидаемый `alignof` |
| --- | --- | --- |
| `First` | 4 | 4 |
| `Second` | 1 | 1 |
| `Member` | 8 | 8 |
| `Derived` | 32 | 8 |
| `Padded` | 24 | 8 |
| `Packed` | 16 | 8 |
| `Empty` | 1 | 1 |
| `EmptyDerived` | 4 | 4 |

`First` хранит один `int`, `Second` — один `char`, `Member` — один указатель.
У этих классов нет виртуальных функций или виртуальных баз, поэтому
дополнительных указателей для виртуальности не ожидается.

Ожидаемое размещение `Derived`:

```text
смещение 0..3    First::a_
смещение 4       Second::b_
смещение 5..7    padding перед первым Member
смещение 8..15   one_.name_
смещение 16..23  two_.name_
смещение 24..31  three_.name_
```

В `Padded` поле `c_` занимает байт 0. Байты 1..7 — padding, чтобы `d_`
начиналось со смещения 8. `d_` занимает байты 8..15, `e_` — байт 16.
Байты 17..23 дополняют размер объекта до кратного выравниванию 8.

В `Packed` поле `d_` занимает байты 0..7, `c_` — байт 8, `e_` — байт 9.
Остаётся только хвостовой padding в байтах 10..15. Поля те же, но их порядок
позволяет убрать промежуток перед `double`. Имя `Packed` само по себе
не включает специальную упаковку: выравнивание `double` остаётся обычным.

`sizeof(Empty)` не ноль: у отдельных объектов должны быть различимые адреса,
и размер полного объекта даже пустого класса положителен.

У `EmptyDerived` пустая база может не занимать дополнительных байтов
(empty base optimization). Ожидается, что начало базы и `value_` совпадут
с началом объекта, поэтому достаточно 4 байт для `int`.

## 3. Приведение к базам

Если начало `Derived` имеет адрес `D`, ожидаются такие адреса:

| Указатель | Адрес | Сдвиг от начала объекта |
| --- | --- | --- |
| `&d` | `D` | 0 |
| `static_cast<First*>(&d)` | `D` | 0 |
| `static_cast<Second*>(&d)` | `D + 4` | 4 |

Все три адреса не совпадут: первые 4 байта занимает `First::a_`, а
`Second::b_` находится после него.

`static_cast<Second*>(&d)` знает отношение наследования и корректирует
адрес до подобъекта `Second`. `reinterpret_cast<Second*>(&d)` такого
преобразования к базе не выполняет: для этих типов ожидается исходный
адрес `D`, который не указывает на подобъект `Second`.

Это объясняет требование к `ctx` из занятия 2.1. `void*` не хранит
информацию о типе и расположении баз. Если в подписку передали `Derived*`,
сначала нужно восстановить именно `Derived*`. Затем при необходимости
можно привести его к `Second*` обычным преобразованием к базе.
Прямой `static_cast<Second*>(ctx)` не выполнит нужное смещение от `Derived`.
В агенте передаётся `Agent*` и восстанавливается `Agent*`.

## 4. Ромб

В `DiamondPlain` два подобъекта `Base`: один через `LeftPlain`, другой
через `RightPlain`. Ожидаемый размер — 8 байт: два `int` со смещениями 0 и 4.

В `DiamondVirtual` один общий подобъект `Base`. Для выбранного Linux ABI
ожидается размер 24 байта и выравнивание 8:

```text
смещение 0..7    служебный указатель части LeftVirtual
смещение 8..15   служебный указатель части RightVirtual
смещение 16..19  общий Base::value_
смещение 20..23  хвостовой padding
```

Служебные указатели нужны для нахождения виртуальной базы. В этом ABI
они ведут к таблицам, содержащим в том числе смещения виртуальных баз;
их наличие здесь связано с виртуальным наследованием.
Ожидается, что `DiamondVirtual` больше `DiamondPlain` в 3 раза: 24 / 8.

У `DiamondVirtual` обращение `dv.value_ = 7` однозначно: поле относится
к единственному общему `Base`.

Для обычного ромба строка из задания:

```cpp
DiamondPlain dp;
dp.value_ = 7;
```

должна дать ошибку неоднозначного обращения к `value_`: компилятор
не может выбрать один из двух подобъектов `Base`. Уточнить путь можно так:

```cpp
dp.LeftPlain::value_ = 7;
dp.RightPlain::value_ = 8;
```

Это два независимых поля. Некомпилируемый вариант оставлен здесь,
а исходник упражнения не изменялся.
